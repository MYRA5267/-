# Репозиторий

Здесь живут два продукта на общей основе: Next.js, Supabase Postgres,
Telegram Mini App, вход по подписанному `initData`, изоляция данных
в политиках базы.

| Продукт | Где | Спека |
| --- | --- | --- |
| **PULSE Studio** — центр управления контентом | `/pulse`, схема `pulse` | `docs/pulse_studio_spec_ru.md` |
| **ОБА** — Mini App для двоих | `/`, схема `public` | `docs/oba_claude_code_spec.md` |

Продукты не пересекаются: разные схемы, разные роуты, разные политики.
Общее только то, что и должно быть общим — проверка `initData`
(`src/lib/telegram/verify.ts`) и пул соединений (`src/lib/db/pool.ts`).

# PULSE Studio

Одна идея превращается в согласованный пакет публикаций для всех нужных
площадок за несколько минут, а результат возвращается в систему и
улучшает следующий материал.

```
Идея → материалы → адаптация под площадки → одобрение → публикация → метрики → следующая гипотеза
```

Главный принцип: ИИ выполняет рутину, но последнее решение остаётся за
человеком. Ничего не публикуется без явного одобрения, и одобряется
конкретный снимок текста — правка после одобрения сбрасывает статус.

Что сделано, что сделано частично и почему — в `docs/pulse_status.md`.

## Запуск

```bash
cp .env.example .env.local
npm install
npm run db:push            # прогнать supabase/migrations/*.sql
npm run pulse:rls-check      # убедиться, что RLS не пускает лишнего
npm run pulse:publish-check  # очередь: отправка, повтор без задвоения, самопочинка
npm run dev                  # приложение на /pulse
npm run pulse:worker         # очередь публикаций, отдельным процессом

node scripts/pulse-smoke.mjs # сквозной путь по HTTP: идея → очередь → сводка
```

Минимум для старта — `DATABASE_URL` и `TELEGRAM_BOT_TOKEN`.
Локально без Telegram: `PULSE_ALLOW_DEV_AUTH=1` и `PULSE_DEV_TG_ID=910000001`
в `.env.local`. В production этот путь выключен жёстко.

Остальные переменные по мере надобности:

- `ANTHROPIC_API_KEY` — включает генерацию. Без него продукт работает:
  версии собираются как раскладка идеи по формату площадки, и приложение
  честно показывает, что модель не участвовала.
- `PULSE_TOKEN_KEY` — 32 байта для шифрования токенов площадок.
- `PULSE_WORKER_SECRET` — им подписан служебный вызов очереди.

## Как устроен доступ к базе

Одна дверь: `src/lib/pulse/auth.ts` берёт `tg_id` только из подписанного
`initData`, никогда из тела запроса.

Дальше два пути в `src/lib/pulse/db.ts`:

- `withUser(tgId, fn)` — обычный путь. Транзакция с
  `set local role authenticated` и `app.tg_id`, всё под RLS.
- `withAdmin(fn)` — владелец схемы, RLS не действует. Только там, где
  человек про себя ещё ничего не может: завести себя при первом входе,
  создать пространство, войти по коду. И worker — он читает токены и
  пишет публикации, чего роли `authenticated` не дают.

Изоляция арендаторов и роли живут в политиках
(`supabase/migrations/0002_pulse.sql`), а не в коде приложения.
Токены площадок не просто скрыты — их колонки не входят в `grant`,
поэтому frontend не получит секрет даже при ошибке в коде.

## Правила публикации

Они же — то, что проверяется тестами:

1. Ничего не публикуется без явного одобрения человека.
2. Одобряется конкретный снимок текста и медиа.
3. Любая правка после одобрения сбрасывает статус в review.
4. Время хранится в UTC, показывается в часовом поясе проекта.
5. Перед отправкой проверяется снимок, срок токена и лимиты площадки.
6. Временные ошибки повторяются с растущей задержкой, постоянные
   останавливают задачу и уведомляют владельца.
7. Повторный запрос после сетевой ошибки не создаёт второй пост:
   ключ идемпотентности считается от одобренного снимка.
8. Секреты и токены не возвращаются во frontend.
9. Для неподключённой площадки создаётся экспорт-пакет.

## Уровень автоматизации — честно

Полностью автоматически публикует **Telegram**: бот должен быть
администратором канала с правом публикации.

**Threads, Instagram, TikTok** в первом релизе готовят материал и отдают
пакет для ручной загрузки. Публикация через официальные API включается
после production-доступа Meta, App Review и одобрения `video.publish` —
обещать публичный автопостинг в первый день нельзя. Каждая площадка
реализована отдельным модулем с общим интерфейсом, поэтому изменение
одного API не ломает всю систему.

# ОБА

Telegram Mini App для двоих. Спека — `docs/oba_claude_code_spec.md`,
визуальный референс — `docs/oba_miniapp_prototype.html`.

Сделан пункт 1 из «Порядка работы»: схема + RLS + проверка `initData` +
связка пары по коду.

```bash
npm run db:rls-check   # проверка политик схемы public
```

Одна дверь — `src/lib/auth.ts`, два пути в `src/lib/db/pool.ts`
(`withUser` под RLS, `withAdmin` для того, чего человек про себя ещё не
может). Изоляция пары и секретный слой живут в политиках
(`supabase/migrations/0001_init.sql`): секретный пункт физически не
выходит из Postgres к партнёру.

Первый вход создаёт пару и код из 6 символов. Второй вводит код —
`unique (couple_id, ink)` на `users` закрывает связку навсегда.
